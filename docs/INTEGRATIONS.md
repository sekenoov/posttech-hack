# Интеграции: 1С:ЗУП и Documentolog

> **Реальные интеграции в прототипе не выполнены.** Работают mock-адаптеры с синтетическими данными. Документ описывает, где и как подключаются настоящие системы.

## Принцип

Бизнес-логика (`services/`, `routers/`) зависит только от интерфейсов-портов в `backend/app/integrations/ports.py`. Адаптер выбирается в `integrations/__init__.py` (`get_hr_provider()`, `get_docflow_provider()`). Каждый вызов пишется в таблицу `integration_events`; HR видит журнал на странице «Интеграции».

```
services/leave.py ──► DocumentFlowProvider ──► MockDocumentolog      (сейчас)
                                          └──► DocumentologAdapter   (развитие)
seed.py / sync ─────► HRMasterDataProvider ──► Mock1CZup             (сейчас)
                                          └──► OneCZupAdapter        (развитие)
```

## 1С:ЗУП → JanaМен

| | |
|---|---|
| Порт | `HRMasterDataProvider`: `list_employees()`, `get_employee(code)` |
| Mock | `mock_1c_zup.py` читает `seed_data/org.json` |
| Направление | только из 1С:ЗУП в JanaМен; JanaМен не пишет в 1С |
| Данные | табельный номер, ФИО, должность, подразделение, руководитель, дата приёма, право на отпуск |
| Где хранится | `EmployeeProfile` (read-only копия с `source` и `synced_at`), `User.manager_id`, `LeaveBalance` |

**Как подключить реально:**
1. Реализовать `OneCZupAdapter` с теми же методами поверх HTTP-сервиса или OData-публикации 1С:ЗУП.
2. Добавить задание синхронизации (ночное и по запросу HR): upsert `EmployeeProfile` по табельному номеру, пересчёт `manager_id`, обновление `LeaveBalance`.
3. Новым сотрудникам создавать учётную запись и отправлять приглашение; уволенных отключать (`is_active = false`), а не удалять.
4. Учётные данные 1С — через переменные окружения или хранилище секретов.

Форма «Добавить сотрудника» в админке нужна только для тех, кого ещё нет в выгрузке (`source = manual`).

## JanaМен → Documentolog

| | |
|---|---|
| Порт | `DocumentFlowProvider.submit_leave_order(request_id, employee_code, full_name, start_date, end_date, days)`; `cancel_leave_order(document_id, request_id)` при отзыве согласования |
| Mock | `mock_documentolog.py` возвращает номер `DL-<год>-<номер заявки>` и статус `sent_for_signing` |
| Когда вызывается | сразу после согласования заявки (`services/leave.py`); при отзыве согласования приказ отзывается, `docflow_ref` очищается, при повторном согласовании уходит новый |
| Результат | номер документа сохраняется в `LeaveRequest.docflow_ref` и показывается в карточке заявки |
| Сбой | не блокирует согласование: пишется событие `error` в журнал интеграций; автоматическая повторная отправка — в развитии (см. ниже) |

**Как подключить реально:**
1. Реализовать `DocumentologAdapter`: создать проект приказа на отпуск из шаблона, указать подписантов, вернуть ID документа.
2. Добавить webhook `POST /integrations/documentolog/webhook` для статусов подписания (подписан / отклонён) → запись в историю заявки и уведомление сотруднику.
3. Повторная отправка при сбое — фоновая задача по событиям `error`.

## Что видно в прототипе

- HR → «Интеграции»: карточки обеих систем (порт, адаптер, направление, данные, последний вызов) и журнал вызовов.
- Карточка согласованной заявки: «Приказ в Documentolog (демо): DL-…».
- Профиль: «Данные получены из 1С:ЗУП (демо-интеграция)» и время синхронизации.
